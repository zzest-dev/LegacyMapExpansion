# Применяемая структура MapPro

Документ описывает подмножество MapPro, используемое этим переносом. Это не замена полной спецификации всех редакторских компонентов. Числа little-endian, координаты и transform — float32, строка — int32 длины UTF-8 в байтах и сами байты.

## FileBlocks

Контейнер начинается тремя int32: magic `112233`, размер таблицы и число блоков N. Далее идут N int32 с размерами блоков. Размер таблицы равен `4 + 4*N` и включает поле N. Начало данных: `8 + tableBytes`. Блоки следуют подряд; сумма длин с заголовком должна совпадать с длиной файла.

Блок 0 содержит int32 `11223344` и строку `MapPro_FileBlocks`. Последний блок содержит метаданные карты. Остальные блоки используются для ячеек дерева и дополнительных данных записей. Числа-ссылки — индексы блоков, а не смещения в байтах.

## Метаданные

В начале метаданных: version, nextId, nextInfoId. Для читаемого v16 перед числом ресурсов имеется ещё одно int32. Затем число ресурсов и записи каталога:

```text
int32 id
string guid
string assetPath
bool isDecal
bool isServer
float32 dists[6]
```

После каталога: число корневых ячеек, затем тройки int32 `(x, z, blockId)`. Для каждой ячейки считывается указанный блок.

## Ячейка

Сначала int32 количества размещений. В v16 перед transform каждого размещения есть int32 instanceId; в выходном v15 этого поля нет. Далее:

```text
float32 position[3]
float32 scale[3]
float32 eulerRotation[3]
int32 resourceId
int32 payloadBlockId
```

Если payloadBlockId > 0, за записью идут byte числа точек viewLine и соответствующие тройки float32. Содержимое самого дополнительного блока здесь не декодируется. У обычных импортируемых статических записей payload равен -1.

После размещений идут int32 количества дочерних ячеек и тройки `(x, z, blockId)`. В используемом quadtree не больше четырёх детей. Читатель проверяет ссылки, границы блоков и повторное посещение ячеек. Нельзя предполагать, что каждый промежуточный блок является ячейкой: часть блоков хранит payload.

## Радиус видимости и дерево

Для масштабов `(sx,sy,sz)` и `dists = d[0..5]` используемая игрой величина:

```text
radius = sqrt(max(
  abs(d0*sx*sz), abs(d1*sx*sz),
  abs(d2*sz*sy), abs(d3*sz*sy),
  abs(d4*sx*sy), abs(d5*sx*sy)
) * 1000 / 0.3)
```

Для размещений с viewLine к ней добавляется максимальная длина локального вектора точки линии. Значение `max(dists)` само по себе не является дальностью в метрах.

Корневая ячейка имеет размер 1000. На глубине depth размер равен `1000 / 2^depth`. Если радиус больше половины текущего размера, объект остаётся в текущей ячейке; иначе спускается в подходящего ребёнка, но не глубже 4. Сторона ребёнка выбирается строгим сравнением `x > centerX` и `z > centerZ`: равенство относится к нижней стороне.

Штатное преобразование координаты в индекс ячейки:

```text
n = coordinate / cellSize + 0.5
if n < 0: n -= 1
index = truncateTowardZero(n)
```

Оно отличается от обычного округления и на отрицательных точных границах — от простой формулы floor. Для совпадения с движком учитывайте вычисления float32 и порядок детей. Неправильная ячейка особенно заметна на крупных зданиях: они появляются поздно, даже когда их дистанция видимости настроена правильно.

## Неизвестные дополнительные данные

Компоненты редактора и игровые объекты могут использовать собственные payload. Не переносите новые версии этих данных в PC без отдельного понимания схемы. Текущий перенос сохраняет исходные PC-payload побайтно, перенумеровывает ссылки при создании нового контейнера и переносит новые модели как статическую геометрию.

Контейнер всегда следует создавать заново, затем проверять чтением. Вставка байтов на месте без пересчёта размеров и ссылок повреждает файл.
